# POC: evaluación de dependencias en CI

Este repositorio contiene once escenarios de laboratorio versionados (S0–S10). Sus manifiestos, lockfiles y fixtures no se generan ni se modifican durante la ejecución. GitHub Actions analiza esos archivos y produce una decisión con evidencia. Para escenarios npm elegibles, crea una copia temporal e instala las versiones fijadas con `npm ci --ignore-scripts`; no ejecuta scripts de ciclo de vida ni código de aplicación. Para Ruby y Maven, el control de integridad descarga únicamente artefactos de dependencias directas a un directorio temporal. S10 es la excepción deliberada: ejecuta una prueba de S0 dentro de Docker Compose e instala las gems dentro del contenedor efímero.

## Flujo  conceptual

En cada `push` o `pull request`, el workflow [`.github/workflows/dependency-security-assessment.yml`](.github/workflows/dependency-security-assessment.yml), **Evaluación de seguridad de dependencias**, ejecuta un único job que recorre `esenario/s*`; no crea un job por escenario. También se puede iniciar manualmente. El job ejecuta Trivy para vulnerabilidades y licencias, inspecciones estáticas de origen/lockfile/scripts, y verificaciones de integridad por ecosistema. En proyectos npm con lockfile consistente y fuentes autorizadas, crea una copia temporal, ejecuta `npm ci --ignore-scripts` y luego `npm audit signatures`. Si el precontrol encuentra fuentes no autorizadas o inconsistencias, omite la instalación. Para RubyGems y Maven verifica los hashes de las dependencias directas contra los metadatos/checksums de sus registros. Si un escenario contiene `compose.yaml`, `compose.yml`, `docker-compose.yaml` o `docker-compose.yml`, el workflow prepara y analiza con `trivy image` las imágenes declaradas y ejecuta el servicio Compose convencional `test`; sus reportes de imagen y de pruebas se incorporan a la evaluación. Cosign valida bundles Sigstore cuando el registro publica uno y hay una identidad confiable configurada. Para tarballs ya versionados, se mantiene la comparación SHA-512 con el SRI publicado por npm. El job consulta además metadatos npm para la señal de mantenimiento. Los reportes JSON, el resumen Markdown, las versiones de herramientas y la base de Trivy se publican como artifacts y se guardan en la rama `evidencias`.

### Conservación y ubicación de las evidencias

Al terminar cada ejecución, el workflow copia los archivos disponibles de `reports/` a la rama **`evidencias`**, incluso si fallaron pasos anteriores. Cada ejecución tiene su propia carpeta, sin sobrescribir las anteriores:

```text
evidencias/runs/<run_id>/<run_attempt>/reports/
```

Allí quedan los JSON de evaluación y escaneo, además del resumen `assessment-summary.md`. Para encontrarlos en GitHub, abre **Code**, selecciona la rama `evidencias` y navega a `runs/<run_id>/<run_attempt>/reports/`. El `run_id` y el `run_attempt` se ven en la URL de la ejecución de Actions; los reintentos de una misma ejecución tienen distinto `run_attempt`.

La copia en la rama del repositorio no depende de la retención de artifacts de Actions (actualmente 30 días): permanece disponible mientras se conserve la rama y el repositorio. Los artifacts de Actions se mantienen además como acceso directo durante su período de retención. El push usa `GITHUB_TOKEN`, por lo que no dispara otra ejecución del workflow. En pull requests desde forks no se guarda en la rama porque GitHub entrega un token de solo lectura; los artifacts de esa ejecución se conservan normalmente.

La política versionada en [`config/dependency-policy.json`](config/dependency-policy.json) establece registros, licencias, umbrales de vulnerabilidad, eventos de ciclo de vida, antigüedad de releases y decisiones ante firmas inválidas, ausentes o no verificables. Para imágenes Compose, las vulnerabilidades `HIGH` y `CRITICAL` de paquetes OS bloquean. También configura el emisor OIDC y las identidades confiables de Cosign. **La política contiene reglas, no resultados esperados por escenario.** [`scripts/assess_dependencies.py`](scripts/assess_dependencies.py) combina la evidencia de Trivy, las inspecciones estáticas y los verificadores npm/Sigstore/Compose. [`scripts/render_assessment_summary.py`](scripts/render_assessment_summary.py) genera el resumen desde los JSON de esa corrida. La precedencia es **bloquear > revisión manual > permitir**. Los hallazgos no hacen fallar por sí solos el workflow ni bloquean el merge.

## Cómo se calcula la decisión

Los archivos de los escenarios (`S0–S10`) son las entradas estáticas de la evaluación: están versionados en el repositorio y el workflow no los genera ni modifica. En cada ejecución se vuelven a analizar y se producen reportes nuevos. Por eso, un mismo commit puede dar resultados distintos si cambia la base de vulnerabilidades/licencias de Trivy o la información consultada en el registro npm, como las fechas de publicación. Las decisiones no están escritas de antemano para cada escenario: se derivan de los hallazgos observados y de la política vigente.

El evaluador aplica estos controles:

| Control | Regla que aplica | Decisión si se incumple |
|---|---|---|
| Vulnerabilidades | Trivy informa una vulnerabilidad `CRITICAL` o con CVSS igual o superior a `9.0`. | **Bloquear** |
| Vulnerabilidades | Trivy informa una vulnerabilidad `HIGH` o con CVSS igual o superior a `7.0`, sin cumplir antes una condición de bloqueo. | **Revisión manual** |
| Licencias | El lockfile o Trivy informa una licencia que no está en la lista permitida: `0BSD`, `Apache-2.0`, `BSD-2-Clause`, `BSD-3-Clause`, `ISC`, `MIT`, `MIT-0` o `Unlicense`. | **Bloquear** |
| Registro de paquetes | Una URL de resolución del lockfile o una configuración `registry` de `.npmrc` no usa HTTPS con el host permitido `registry.npmjs.org`. | **Bloquear** |
| Consistencia del lockfile | Las dependencias directas declaradas en `dependencies`, `devDependencies` u `optionalDependencies` no coinciden con las entradas correspondientes del lockfile. | **Bloquear** |
| Scripts de ciclo de vida | Se encuentra una declaración de `preinstall`, `install`, `postinstall` o `prepare` en un `package.json` del escenario. El comando se detecta, pero no se ejecuta. | **Bloquear** |
| Instalación npm controlada | Para proyectos npm con manifiesto/lockfile consistentes y registros autorizados, `npm ci --ignore-scripts` debe completar en una copia temporal. Si no puede verificarse la instalación, se requiere revisión. | **Revisión manual** |
| Scripts ignorados | En S4 se comprueba que `npm ci --ignore-scripts` no haya creado `postinstall-marker.txt`. Si el marcador aparece, se considera que el hook se ejecutó. | **Bloquear** |
| Firma de paquetes npm | `npm audit signatures` verifica las firmas del registro de los paquetes descargados. Una firma inválida bloquea; una firma ausente o un error de verificación requiere revisión manual. | **Bloquear / revisión manual** |
| Provenance npm | Se conserva la atestación Sigstore que npm reporte, cuando exista. Su ausencia se informa como falta de provenance, no como prueba de firma inválida. | Evidencia contextual |
| Integridad de dependencias Ruby/Maven directas | Se descargan los artefactos directos fijados y se comparan con el hash publicado por RubyGems/Maven Central. Una discrepancia bloquea; si solo hay SHA-1 en Maven, se conserva la coincidencia pero se requiere revisión manual por la debilidad del algoritmo. | **Bloquear / revisión manual** |
| Provenance Sigstore de Ruby/Maven | Si el registro publica un bundle `<artefacto>.sigstore.json`, Cosign verifica la firma, la identidad OIDC y la prueba de inclusión en Rekor contra la política. Si no hay bundle, el reporte lo indica como no publicado; no se declara verificada la provenance. | Evidencia contextual |
| Vulnerabilidades de imágenes Compose | Trivy analiza las imágenes declaradas con `trivy image --scanners vuln --pkg-types os`. Vulnerabilidades `HIGH` o `CRITICAL` en paquetes de sistema operativo bloquean; el escaneo se limita a OS y no atribuye este control a gems o paquetes de aplicación. | **Bloquear** |
| Integridad de artefactos npm | Para cada tarball `.tgz` bajo `artifacts/`, el SHA-512 calculado no coincide con el SRI publicado por npm para el paquete y versión correspondientes. | **Bloquear** |
| Integridad de artefactos | No se puede asociar el tarball con el lockfile o no se puede obtener una referencia SHA-512 verificable del registro. | **Revisión manual** |
| Firma Sigstore de artefactos versionados | Para cada artefacto no npm bajo `artifacts/`, se busca el bundle adyacente `<archivo>.sigstore.json`. Cosign lo verifica contra el emisor OIDC y las identidades confiables configuradas; bundle ausente requerido requiere revisión y firma inválida bloquea. | **Bloquear / revisión manual** |
| Mantenimiento | La última fecha de publicación disponible para una dependencia directa de npm supera los `730` días. | **Revisión manual** |
| Mantenimiento | No se pueden obtener metadatos verificables del registro para estimar la antigüedad. | **Revisión manual** |

Los umbrales, la lista de licencias, los eventos de ciclo de vida, el host permitido y las decisiones ante fallos de fuentes externas se configuran en `config/dependency-policy.json`. En la versión actual, un hallazgo de bloqueo prevalece sobre cualquier revisión manual; una revisión manual prevalece sobre permitir. Si ningún control produce hallazgos, la decisión consolidada es **permitir**. Esto significa que no se activó ninguna regla de esta política; no constituye una garantía de ausencia de riesgos.

**“Bloquear” es actualmente una decisión informada en el resumen, no un bloqueo técnico del merge.** Trivy se ejecuta con `--exit-code 0` y el evaluador termina correctamente aunque la decisión sea `bloquear`; por lo tanto, los hallazgos no hacen fallar por sí solos el job ni impiden fusionar el pull request. Errores técnicos al ejecutar los pasos sí pueden hacer fallar el workflow.

## Matriz de escenarios

| Escenario | Ecosistema / artefactos | Control principal | Herramienta o comprobación | Decisión esperada | Evidencia a conservar |
|---|---|---|---|---|---|
| S0 | Ruby on Rails; `Gemfile`, `Gemfile.lock` | Caso limpio de control: hashes de dependencias directas y análisis sin hallazgos | Comparar los SHA-256 de los artefactos directos descargados con RubyGems; Cosign verifica bundles si están publicados | Permitir | Gem/version, SHA publicado y calculado, resultado de comparación, estado Sigstore y decisión |
| S1 | Java/Maven; `pom.xml` | Vulnerabilidad crítica en `log4j-core:2.14.1` (Log4Shell) | Trivy más checksums de dependencias directas Maven Central; Cosign verifica bundles disponibles | Bloquear | Reporte Trivy, coordenadas y hashes directos, algoritmo de checksum, estado Sigstore y decisión |
| S2 | npm; `package.json`, `package-lock.json`, `.npmrc` | Registro y URLs de resolución no autorizados | Inspeccionar `.npmrc` y URLs del lockfile contra la política de registros permitidos | Bloquear | `.npmrc`, URLs detectadas, regla aplicada y decisión |
| S3 | npm; manifiesto y lockfile | Inconsistencia entre versiones declaradas y resueltas | El control estático identifica la inconsistencia y omite la instalación para no resolver un árbol distinto | Bloquear | Valores comparados, motivo de omisión y decisión |
| S4 | npm; manifiesto y fixture local | Script `postinstall` presente; comprobar la supresión del hook | Inspección estática y `npm ci --ignore-scripts` en una copia temporal; comprobar que no aparece el marcador | Bloquear por presencia del hook | Declaración detectada, ruta, estado de la instalación, resultado de firmas y estado del marcador |
| S5 | npm; tarballs original y alterado | Integridad de los bytes versionados frente al SRI publicado por npm | Calcular SHA-512 de los tarballs y contrastarlo con el registro; el control de origen omite `npm ci` para la URL no autorizada del lockfile | Bloquear la copia alterada | SRI, hashes calculados, comparaciones y motivo de omisión de instalación |
| S6 | npm; `package.json`, `package-lock.json` | Antigüedad del último release de `is-promise` | `npm ci --ignore-scripts` y `npm audit signatures`; consultar metadatos del registro para antigüedad | Revisión manual | Reportes de instalación/firmas, metadatos, umbral y decisión |
| S7 | npm; `package.json`, `package-lock.json` | Licencia `GPL-3.0-only` no permitida por la política | Trivy, `npm ci --ignore-scripts` y verificación de firmas del registro | Bloquear | Reporte Trivy, reporte npm de firmas, política aplicada y decisión |
| S8 | npm; `package.json`, `package-lock.json` | Vulnerabilidad alta en `path-to-regexp@0.1.7` | Trivy, `npm ci --ignore-scripts` y verificación de firmas del registro | Revisión manual | Reporte Trivy, reporte npm de firmas, CVE/CVSS y decisión |
| S9 | npm; manifiesto, lockfile y `.npmrc` | Riesgos combinados: origen no autorizado y vulnerabilidad/integridad | El precontrol de origen bloquea y omite `npm ci`; Trivy y controles estáticos continúan | Bloquear | Evidencia de origen, motivo de omisión, reportes Trivy y decisión consolidada |
| S10 | Mismo Rails, Gemfile y Gemfile.lock de S0; Docker Compose | Vulnerabilidad en un paquete del sistema operativo de la imagen Ruby Alpine | Iniciar Rails y realizar una solicitud HTTP a `GET /health` en el servicio `test`; analizar la imagen fijada por digest con `trivy image --pkg-types os` | Bloquear por vulnerabilidad OS `HIGH`/`CRITICAL`; la prueba debe pasar | Digest y referencia de imagen, reporte Trivy OS, CVE/paquete/severidad, salida y estado de la prueba Compose |

## Reglas de interpretación

- Trivy analiza vulnerabilidades y licencias. El evaluador aplica controles separados para origen, consistencia del lockfile, lifecycle scripts, firmas npm, bundles Sigstore, integridad SRI y antigüedad del release.
- Los escenarios y sus archivos de entrada permanecen fijos; por ello, las comprobaciones estáticas deberían producir la misma evaluación para el mismo commit y configuración. Los resultados que consultan fuentes externas (en particular la base de vulnerabilidades/licencias de Trivy o metadatos del registro) pueden variar al actualizarse esas fuentes. Registrar versiones de herramientas, fecha de observación y versión/fecha de la base de Trivy para interpretar cualquier diferencia.
- `npm ci --ignore-scripts` se limita a copias temporales de escenarios npm con lockfile consistente y registros permitidos. No instala en S0/S1, y se omite en escenarios con origen no confiable o lockfile inconsistente (S2, S3, S5 y S9 en los fixtures actuales). Los lifecycle scripts están desactivados explícitamente; S4 conserva además una comprobación del marcador.
- La instalación temporal npm descarga y descomprime paquetes, pero no ejecuta sus lifecycle scripts. El verificador de integridad Ruby/Maven descarga solo artefactos directos para calcular hashes y no instala dependencias transitivas. S10 sí ejecuta `bundle install` y una prueba de `/health` dentro de un contenedor efímero; no ejecuta esos comandos en el host. No se ejecutan `mvn install` ni plugins Maven.
- `npm audit signatures` verifica firmas del registro para los paquetes descargados; su salida de provenance se conserva si la hay. La ausencia de una atestación de provenance se informa por separado y no se interpreta como firma inválida. En npm se conserva la identidad que declara la provenance, pero esta política no mantiene una allowlist por paquete de repositorio/workflow de origen. La evidencia se limita al árbol que npm instala en el runner y a la versión de Node/npm registrada.
- Las dependencias `file:` locales no tienen firma del registro npm. En S4, `lab-postinstall-fixture` queda fuera de esa señal; su control relevante es la detección estática del `postinstall` y la comprobación de que el marcador no aparece con `--ignore-scripts`.
- S10 conserva el fixture Rails y las gems de S0; su condición intencional de bloqueo es la imagen `ruby:3.4.10-alpine3.23` fijada por digest. En la comprobación realizada con Trivy 0.76.2 se identificaron `CVE-2026-107891` en `musl`/`musl-utils` y `CVE-2026-85091` en `zlib`, ambos `HIGH`; el escaneo de S10 usa `--pkg-types os` para excluir vulnerabilidades de gems. La base Alpine mantiene la descarga de la imagen liviana. La prueba hace una solicitud HTTP real a `/health` desde un contenedor efímero con el escenario montado en solo lectura.
- Para otros escenarios Compose, el workflow busca un servicio llamado `test`; si no existe o la prueba/escaneo no puede completarse, queda registrada una revisión manual. Un test exitoso no anula un bloqueo de seguridad de la imagen.
- Cosign solo puede verificar archivos para los que existe un bundle Sigstore y una identidad OIDC confiable configurada. El control Ruby/Maven busca bundles junto a los artefactos directos que descarga; el control de archivos versionados busca `<archivo>.sigstore.json` bajo `artifacts/`. Si el registro no publica provenance, el hash del registro sigue siendo evidencia de integridad de bytes, pero no de origen de build. La política no aplica todavía una allowlist específica de repositorio/workflow por cada dependencia npm.
- S6 y S8 son revisiones manuales, no permisos automáticos. En S9, una condición bloqueante prevalece sobre cualquier señal de revisión.
- Los escenarios son casos de laboratorio diseñados para ejercitar controles. La concordancia con sus decisiones esperadas no estima eficacia general, tasas de falsos positivos o negativos ni cobertura productiva.
- La tesis documenta una corrida real principalmente con npm y una muestra Maven. S0 aporta un fixture Ruby; su presencia no debe presentarse como validación empírica de todo ese ecosistema sin ejecutar y documentar esa evaluación.
- El modo simulado, si se usa para pruebas deterministas del motor, debe mantenerse separado de las corridas reales y no presentarse como evidencia de detección con herramientas reales.

## Criterios de aceptación del pipeline

1. El workflow corre los once escenarios S0–S10 en GitHub Actions en cada `push` y `pull request`, y permite ejecución manual.
2. Cada escenario conserva como artefactos el reporte JSON de Trivy, los metadatos de la base y la decisión consolidada con sus hallazgos.
3. Las instalaciones npm elegibles se ejecutan en un directorio temporal con `npm ci --ignore-scripts`. S10 instala las gems y ejecuta el smoke test de Rails dentro del contenedor efímero. El control de integridad Ruby/Maven solo descarga artefactos directos; no se ejecutan plugins Maven.
4. Los reportes conservan hashes npm/Ruby/Maven, resultados de firmas npm y, cuando existe bundle e identidad de confianza, la verificación Cosign/Sigstore.
5. La política aplica precedencia de bloqueo sobre revisión manual y revisión manual sobre permiso.
6. Si un escenario incluye Docker Compose, el workflow analiza sus imágenes con Trivy y ejecuta su servicio `test`; el informe conserva ambos resultados.
7. El informe identifica qué ecosistemas y controles se ejecutaron o se omitieron; no infiere cobertura a partir de la mera presencia de archivos.
8. Los archivos disponibles de cada ejecución, incluido `assessment-summary.md`, se conservan en `evidencias/runs/<run_id>/<run_attempt>/reports/`, además de los artifacts de Actions.
